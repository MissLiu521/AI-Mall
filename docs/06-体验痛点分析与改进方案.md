# 06 · 商城体验痛点分析与改进方案

> 来源：基于当代电商市场用户反馈的共性问题归集，结合本项目现有架构给出的可落地改进项。
> 结论先行：**用户抱怨的重心已从"买不到"转向"买不明白、等不了、退不掉、问不到人"。**

---

## 一、问题定位

交易链路上的技术故障（下单失败、支付掉单）早已被行业解决，真正的体验缺口集中在三处：

| 断裂带 | 表现 | 用户感受 |
| --- | --- | --- |
| **数据断裂** | 商品、库存、物流、退款数据分散在不同系统，前端拼不出一个连续事实 | "我不知道现在到底什么状态" |
| **权限断裂** | 客服看得到问题，但没有权限执行操作，只能转单 | "说了半天没人能办" |
| **责任断裂** | 物流、商家、平台三方，出问题互相推 | "找不到该找谁" |

---

## 二、Top 6 高频痛点

### 1. 搜索结果不准 / 找货难

反馈量最大、最容易被误判为"算法不行"的一类。拆开是三层：

- **召回不准**：搜"降噪耳机"出一堆蓝牙音箱 —— 词表与商品标题脱节，缺同义词与场景词
- **筛选失效**：筛"500 以下"仍出现 999 的商品 —— 价格/库存/规格未索引到筛选层
- **结果不可解释**：排序黑箱，"凭什么第一个是它"

> **关键洞察**：用户不要求搜索"懂我"，只要求"搜到的都是相关的"。召回率通常没问题，**精确率崩塌**才是流失主因——前 3 个结果不相关，用户就走了。

### 2. 商品信息不透明 —— 决策成本高

下单前用户反复确认但平台不给的信息：

| 缺什么 | 后果 |
| --- | --- |
| 规格实测（尺码、容量、重量） | 买错 → 退货 |
| 库存真实状态（"有货"但下单后缺货） | 超卖 → 投诉 |
| 价格构成（到手价怎么算出来的） | 结算页被"惊喜" → 弃单 |
| 实拍图 / 买家秀（主图精修过度） | 心理落差 → 退货 |

**直接结果是"下单前流失"与"下单后退货"两头漏。**

### 3. 客服"问不到人" / "答非所问"

近年在 AI 客服大规模铺开后**矛盾反而加剧**的区域。

```
用户：我的订单到哪了
机器人：您好，关于物流问题您可以点击"我的订单"查看哦~
用户：……（已经点过了）
```

典型反馈形态：

- 只做分流不做解决，绕三圈回到"转人工"，人工再排 20 分钟
- 上下文丢失，换客服要重新描述
- **无法执行操作**：用户要退款，机器人只能说"已为您记录"
- 排队不透明；夜间无人值守

> **这是"AI 客服"最被诟病的点：把"回答"当成了"解决"。**

### 4. 物流信息失真 —— 等待焦虑

- 长期停在"已揽收"，无异常说明
- "预计明天送达"跳票且不主动通知
- 派送失败无原因、无重派入口
- 多包裹只给一个总单号

**核心不是慢，是"不知道"。用户能接受 5 天到货，不能接受第 3 天还不知道东西在哪。**

### 5. 售后与退款流程摩擦（流失最强触发器）

情绪最容易被放大的一环：

| 摩擦点 | 用户感受 |
| --- | --- |
| 不告诉你能不能退 | "我到底符不符合条件？" —— 靠猜 |
| 先寄回再审核 | 钱货两空的不安全感 |
| 进度不透明 | "提交 3 天没动静" |
| 金额被扣 | "为什么少 12 块？" 无明细 |
| 反复举证 | 拍图、写说明、被驳回、再拍 |

> **一次糟糕的售后，损失的不是这一单，是这个用户之后的全部订单。** 敢买本身，就是信任。

### 6. 结算与支付"最后一公里"摩擦

强制登录看价、优惠券不能自动选最优、运费最后一步才出现、表单字段过多、支付失败无原因、超时取消与支付并发冲突。

**结算页每多一个必填项，就掉一批人。**

---

## 三、两条反直觉反馈

**① 用户不讨厌机器人，讨厌"假装能解决问题的机器人"。**
若一开始就明示"我只能查物流，退款需转人工"，接受度远高于绕三圈再转人工。**预期管理比能力本身更重要。**

**② "功能太多"本身就是痛点。**
C 端高频路径只有 4 条：**搜 → 看 → 买 → 退**，其余入口都是干扰。

## 四、痛点 → 本项目能力映射

| 痛点 | 本项目现状 | 本次改进 |
| --- | --- | --- |
| 搜索不可解释 | 有 2-gram 分词打分，但只输出"高度相关/较为相关" | **逐条输出具体匹配理由**（命中标题词/标签/价格约束）+ 匹配度分数 |
| 搜索零结果 | 直接返回空列表 | **零结果兜底**：给出放宽建议与相近品类 |
| 规格不透明 | 只有 tags 与描述 | 商品详情新增**规格实测表**（结构化 spec 字段） |
| 库存含糊 | 只有数字 | 详情页**库存状态分档文案**（充足/紧张/仅剩 N 件/缺货预告） |
| 价格不清 | 只有 price / compareAt | 新增**价格构成明细**（原价 - 立减 = 到手价，运费规则前置） |
| 退货靠猜 | 有资格判定，但埋在订单详情底部 | 商品页**前置"退货政策 + 一键判定"**；订单页时间轴 |
| 退款进度黑箱 | 仅有 pending/approved/rejected 三态 | **退款时间轴**：每步写明谁在处理、预计多久、当前卡在哪 |
| 客服绕圈 | Agent 已能真实执行退款 | **能力边界明示**：入口即展示"我能直接办的事"与"需转人工的事" |
| 客服答完不办事 | 工具调用后仅返回文本 | 回复中标注**已执行的动作与结果**（如"已为你提交退款 RD-xxx"） |

## 五、改进项优先级

| 优先级 | 改进项 | 理由 |
| --- | --- | --- |
| P0 | 搜索理由 + 零结果兜底 | 影响最大流量入口，改动成本低 |
| P0 | 退款时间轴 | 售后是流失最强触发器，且数据已有 |
| P0 | 客服能力边界明示 | 差异化卖点，且直接回应最大情绪点 |
| P1 | 商品规格/库存/价格透明 | 降低决策成本与退货率 |
| P1 | 商品页退货政策前置 | 把"能不能退"从猜变成确定 |
| P2 | 物流异常主动说明 | 当前为 Mock 物流，先做状态语义化 |

---

## 六、验收标准

1. 搜索结果每条带 `matchReasons`（至少 1 条命中理由），前端以标签形式展示
2. 搜索无结果时返回 `suggestions`，前端展示可点击的放宽条件
3. 订单进入退款流程后，详情页展示含时间戳、责任方、预计时效的时间轴
4. 商品详情展示规格表、库存分档、价格构成、退换政策
5. AI 客服入口展示能力清单，且正式回复中区分"已执行"与"仅解答"
6. 全部既有测试不回归；新增能力有对应测试用例
