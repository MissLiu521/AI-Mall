## 二、P0：上线阻断项（必须优先处理）

### P0-1 静态资源存在路径穿越，可读取任意文件（安全，已实测）

- **证据**：`server/src/routes/index.js:225-228` 先 `decodeURIComponent(url.pathname)`，再 `path.join(distDir, ...)` 后直接 `readFileSync`，没有校验解析结果是否仍在 `dist` 内。
- **实测**：
  - `GET /..%2f..%2fserver%2fsrc%2fdb%2fschema.js` → **200，3980 字节**
  - `GET /..%2f..%2fpackage.json` → **200，返回项目 package.json**
  - 同理可读 `server/data/mall.db`（含用户邮箱、密码哈希、收货地址、订单）
- **影响**：只要生产环境存在 `web/dist`（`npm run build` 后必然存在），公网即可下载源码与数据库。这是本次检查中风险最高的一项。
- **修复**：
  1. `const filePath = path.resolve(distDir, '.' + pathname)`，随后校验 `filePath === distRoot || filePath.startsWith(distRoot + path.sep)`，否则 404；
  2. 拒绝包含 `%2f`、`%5c`、`..` 的请求；
  3. 静态资源未命中返回 404，不要回退 `index.html`（只对无扩展名路由回退）；
  4. 改用 `fs.createReadStream`，补充 `Content-Type`、`Cache-Control`、`ETag`。
- **验收**：上述两个 URL 均返回 404；`/assets/*.js`、`/` 正常。

### P0-2 支付是假的，且前端"下单即已支付"

- **证据**：`orders.js:110-116` 的 `payOrder` 只改状态；`Checkout.vue:54`、`mobile/cart.vue:32`、`mobile/detail.vue:55` 创建订单后立刻调用 `/pay`。
- **影响**：
  - GMV、客单价、成交趋势全部无业务意义；
  - 无法验证支付回调、超时关单、重复支付、退款原路退回等真实链路；
  - 对外演示时用户会认为"已经付过钱"，容易造成误解。
- **说明**：README 已声明"支付为 Mock"，属于**已知限制**，但它是"能不能真做生意"的第一道门。
- **建议**：接入微信小程序支付 + 支付宝 APP/小程序支付；下单只生成 `pending_payment` 并返回支付参数；由**回调**驱动 `paid`，回调需验签 + 幂等；补支付流水表与对账任务。

### P0-3 移动端收货地址是硬编码的

- **证据**：`mobile/src/pages/cart/cart.vue:29`、`mobile/src/pages/detail/detail.vue:52` 直接传死地址 `北京市朝阳区建国路 88 号 SOHO 现代城 B 座 1203`；全项目移动端只有订单详情**展示**地址，没有任何地址输入页。
- **影响**：所有小程序/H5 订单都寄往同一个假地址，履约环节直接断裂；小程序一旦对外，属于必现事故。
- **修复**：新增地址簿（增删改、默认地址、手机号校验）+ 移动端确认订单页（商品、地址、备注、运费、支付方式）；订单落库时保存地址快照与结构化字段（收件人/电话/省市区/详址）。

### P0-4 订单生命周期不闭环：不能取消、不能确认收货、不会自动关单

- **证据**：全后端检索，`cancelled` / `completed` **没有任何写入点**（仅种子数据和判断分支出现）；`orders.js:102` 下单即扣库存且 `sales+1`；`orders.js:154` 却提示"订单还未支付，无需退款，可直接取消"——但没有取消接口。
- **影响**：
  - 待支付订单永久占用库存，库存只减不回（`payOrder` 失败、用户放弃支付都会造成库存泄漏）；
  - 已发货订单永远到不了"已完成"，15 天售后时效只能拿 `shipped_at` 当签收回执，语义错误；
  - 用户侧无法自助取消，只能找客服。
- **修复**：补 `cancelOrder`（事务内回补库存、回退销量）、`confirmReceipt`、15 分钟自动关单、发货 7 天自动确认收货；把合法状态迁移固化成表，所有写操作校验迁移合法性。
- **验收**：待支付 15 分钟后自动取消且库存回补；已发货可确认收货；非法迁移返回 409。

### P0-5 退款驳回会把订单打回"待发货"（状态建模缺陷）

- **证据**：`orders.js:297-299`
  ```js
  run("UPDATE refunds SET status = ? ...", [approve ? 'approved' : 'rejected', ...]);
  run('UPDATE orders SET status = ? WHERE id = ?', [approve ? 'refunded' : 'paid', r.order_id]);
  ```
- **影响**：一笔已发货/已完成的订单被驳回退款后变成 `paid`，商家后台可以**再点一次发货**，物流状态与时间戳全部失真。
- **根因**：`orders.status` 一个字段同时承载**支付状态、履约状态、售后状态**三种语义，必然互相覆盖。
- **建议**：拆成 `payment_status` / `fulfillment_status` / `after_sale_status` 三轴（或至少记录 `status_before_refund` 用于回滚），前端按三轴组合展示。
- **附带**：`decideRefund` 未包事务，退款状态、订单状态、库存回补三步可能部分成功。

### P0-6 认证与接口防护不足（已实测）

| 问题 | 证据 | 实测结果 |
| --- | --- | --- |
| JWT 默认密钥写死 | `services/auth.js:3` `'ai-mall-dev-secret-change-me'` | 未设置 `AUTH_SECRET` 时，任何人都能伪造任意用户/商家的 token |
| 登录/注册无限流 | 无任何限流代码 | 可无限撞库，scrypt 还会拖垮 CPU |
| CORS 反射任意来源且允许凭证 | `index.js:24-25` | `Origin: https://evil.example` 被原样回显 + `Allow-Credentials: true` |
| AI 评分接口无鉴权、无归属校验 | `routes/index.js:85-89` | 未登录 `POST /api/ai/messages/999999/rate` → `{"ok":true,"rated":true}` |
| 入参无校验，内部错误外泄 | `products.js:93` 直接绑定 `+pageSize` | `?pageSize=abc` → 500 `ERR_SQLITE_ERROR: datatype mismatch` |
| 无上限，可一次拉全量 | 同上 | `?pageSize=999999` → 返回全部商品 |
| 无安全响应头 | 全项目无 CSP/X-Frame-Options/HSTS | — |

- **修复顺序**：路径穿越 → 启动强制 `AUTH_SECRET`（缺失直接拒绝启动）→ 登录/AI 限流 → 统一入参校验（数字范围、字符串长度、枚举）→ CORS 白名单 → 错误脱敏（对外只给业务码）→ 评分接口加登录与消息归属校验。

### P0-7 小程序上线合规缺位（与刚配置的 AppID 直接相关）

- 无隐私政策、用户协议页面；无 `wx.login` / 手机号授权；收集邮箱与收货地址但无告知与同意。
- 无账号注销、数据导出入口（《个人信息保护法》要求）。
- 无 HTTPS 域名、request 合法域名、业务域名配置说明（README 只写了"不校验合法域名"，那是开发期做法）。
- 无小程序备案、类目资质、客服电话等审核必填项说明。
- **影响**：微信/支付宝审核大概率驳回；即使过审，用户投诉与合规风险仍在。
- **建议**：上线前补齐隐私协议 + 授权弹窗 + 注销接口 + 备案与域名清单，并把"开发期不校验域名"明确标注为仅限本地。

## 四、P2：规模化与体验完善（可排到下一阶段）

- **工程基建**：无 `.gitignore`（`node_modules`/`dist`/`*.db`/`.env` 均无保护）、无 `.env.example`、无 CI、无 Dockerfile、无 lint/format、无 LICENSE。
- **数据库**：无迁移机制，`schema.js` 只有 `CREATE TABLE IF NOT EXISTS`，线上加字段不会生效；无备份/恢复脚本；SQLite 单机适合演示，多实例需换 Postgres。
- **性能**：静态文件 `readFileSync` 同步阻塞事件循环；无 gzip/brotli、无缓存头、无 ETag。
- **可观测**：仅 `console.error`；`/api/health` 不检查 DB；无结构化日志、无指标、无告警；AI 有 Trace 但无失败率/延迟分位看板。
- **测试**：仅后端 87 个用例（README 仍写 68，已漂移）；Web 与 Mobile 无单测/E2E 入 CI。
- **前端体验**：404 被重定向到首页（`router.ts:47`），坏链接无提示；无全局错误边界；图片仍是 emoji，无上传/对象存储/CDN；SPA 无 SSR，SEO 为零。
- **检索**：`searchProducts` 每次全表加载 + 内存 2-gram 匹配，商品上千后延迟线性增长。
- **增长能力**：无收藏、浏览历史、评价晒单、分享、优惠活动配置、Push/订阅消息。
- **多端**：移动端无后台；H5/小程序无分享卡片；小程序未接 `wx.login`（刚配好 AppID，建议下一步就做，邮箱输入在小程序里体验很差）。
- **无障碍与国际化**：图片无 alt、无语义标签补充、无 i18n（当前单语可接受）。

## 五、做得好的地方（避免误伤）

- AI 工具层有白名单、角色校验、3s 超时、结果截断，写操作真实落库，不是"假演示"。
- 可解释检索（`matchReasons`）、零结果放宽建议、退款三步时间轴，确实对应真实痛点。
- 金额全用整数分存储，避免浮点误差；下单有幂等键 + 事务；SQLite 开了 WAL 与外键。
- 降级透明：本地引擎/远端模型在 UI 明示，不假装。
- 后端零依赖、87 个测试可复现，代码结构清晰，服务层是唯一写库处。

## 六、建议的落地顺序

### 第 1 天：安全止血（不改业务）

1. 修路径穿越，静态未命中回 404；
2. `AUTH_SECRET` 未配置则拒绝启动；
3. 评分接口加鉴权 + 归属校验；
4. 入参统一校验（page/pageSize 上下限、pageSize 非法回 400 而不是 500）；
5. CORS 改为白名单；错误响应不透出 SQLite 错误码；
6. 登录/AI 接口限流。

### 第 1 周：交易闭环

- 订单状态拆三轴，补取消 / 自动关单 / 确认收货 / 自动完成；
- 退款驳回恢复原状态，退款决策包事务；
- 移动端补地址簿 + 确认订单页，删除硬编码地址；
- 时间统一 ISO8601 + 前端本地化。

### 第 2 周：支付与履约

- 微信/支付宝支付接入（沙箱先行）+ 回调验签/幂等 + 支付流水；
- 发货录入运单号，订单详情展示物流；
- 后台订单分页/筛选/导出。

### 第 3–4 周：AI 可运营

- "转人工"闭环（工单 + 商家会话 + 通知）；
- 会话历史、AI 退款确认、KB 编辑与检索升级；
- 30–50 条评测集 + 每日回归 + token 成本看板；
- 修复 `ai_config.model` 不生效。

### 上线前 checklist

- [ ] 隐私政策 / 用户协议 / 账号注销
- [ ] 小程序备案、类目资质、HTTPS 与合法域名
- [ ] 支付商户号与回调域名
- [ ] 数据库备份与恢复演练
- [ ] `.gitignore` + `.env.example` + CI（测试 + 类型检查 + 构建）
- [ ] 压测：下单并发库存不超卖、AI 并发不拖垮事件循环

## 七、结论

**先修 3 件事，这个项目就从"能演示"变成"敢给人用"：**

1. **路径穿越**（今天就能修，风险最高）；
2. **移动端地址 + 订单取消/关单/确认收货**（交易闭环，决定能不能真卖货）；
3. **默认密钥、无限流、无校验**（决定会不会被一把打穿）。

支付、物流、合规是第二梯队，但在"对外真实经营"这个目标下，它们同样是硬门槛，不是可选项。

## 八、修复进展（2026-10-19，本地演示范围）

**约束前提**：用户当前没有独立服务器，目标为「本地运行 + 本地演示」。因此本轮只做**不依赖线上资质**的改造；必须备案、商户号、HTTPS 域名才能做的事，明确标注为「本地不覆盖」，而不是假装做了。
